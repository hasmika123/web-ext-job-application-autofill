Resume Builder and Common Profile

One profile as the source of truth, one document JSON per built resume, templates as code, and a PDF that is exactly the preview. This page shows the design from docs/RESUME-BUILDER-DESIGN.md with mockups you can click. Mockups are simplified sketches of the wireframes in section 9 of that doc, not final UI.

A · Executive summary

Ten ideas that hold the design together

The first card is the principle; the rest follow from it.

B · Common Profile onboarding

From nothing to a complete profile by confirming, not typing

Three paths (Upload, Paste, Start fresh) lead into the same card-by-card review, then a completeness meter. Nothing is saved until the user keeps it; the whole batch is one import call.

Try it

    • Pick a path: Upload (existing AI parse, with consent), Paste (LinkedIn "Save to PDF" text), or Start fresh (six questions, chips first).
    • Review: one card per experience, education or project. Keep (swipe right), Edit, Skip (swipe left). Buttons always exist.
    • Skills: a chip cloud: tap to remove, type to add, suggestions from the parsed text.
    • Finish: the meter names the one next action. Weights sum to 100: identity+contact 15, location 5, headline 5, summary 10, experience 25, education 10, skills 15, links 5, preferences 10.

    Simplified: the meter here only counts the sample cards you keep, with the doc's weights as a rough guide; the real score is computed on the server (GET /api/profile/completeness).

    D · Templates

    Switching a template changes one string, never the content

    A template is a render of (ResumeDocument, Theme). Pick one below: the same sample document is re-rendered by a tiny renderer. The check underneath confirms every text fragment of the document is still on the page and the document hash has not changed.

    Compact is two-column: the renderer, not the template, decides what goes in the sidebar, so unsupported sections stay in the main column. It is flagged "caution" for ATS because two columns can be read out of order by some systems. Minimal and Creative arrive in R7.

    Simplified: layouts are re-drawn with plain CSS here; the real templates are React components in @kiwiply/ui that use only .rz-* classes, so preview and PDF share one stylesheet. Printed resumes are always light, even in dark mode.

    E · Architecture

    One document, one render, two outputs

    Every save re-derives parsed_json so the extension, matcher and tailor keep reading what they read today. The PDF is Chromium printing the same HTML as the preview.

    Simplified: the AI proposal service, version rows and the BFF rate limits are left out of the picture.

    F · Data model

    Additive tables, nothing the extension reads changes shape

    Green headers are new. bio.payload is untouched; resume gains two columns. resume_doc is 1:1 with resume so a 100 KB document never rides along in the extension's mirror.

    Key columns only. resume_doc_version and resume_ai_proposal have no foreign key to resume by design (restores of archived resumes stay possible). cover_letter (R5) and resume_share (R7) are reserved and not drawn.

    G · AI and page fit

    Free gets the whole builder; AI is Pro and Autopilot

    Every AI feature is suggest, diff, accept, with server-side truth checks. No streaming, because unchecked text must never be shown.

    AI features by plan
    FeatureTaskFreeProAutopilot

    Simplified: Autopilot is gated exactly like Pro for the builder until Phase 18 (the doc's R0.3 note). Free sees every AI button with a lock and the meter copy; nothing is hidden. "Partial" means a deterministic subset is free.

    The page-fit ladder

    Seven deterministic steps (density, then font size, then margins) are measured in the preview and re-checked in Chromium at export, so output equals preview. If the ladder ends above the page target, the UI offers "Still 2 pages" with the longest items highlighted, and (Pro) an AI "trim the 4 longest bullets". The mini page is an illustration of tightening, not a real layout.
