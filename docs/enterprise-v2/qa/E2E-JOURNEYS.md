> Written 2026-10-15 by Fable (QA architect) against branch `version2` at `0de4f466` (`ent-accounts: S10`). **Design only**: no spec was written or run. A Sonnet agent implements the Playwright specs from these stories; every story is meant to be build-ready (persona, seed, steps, assertions, negative cases, cleanup, run mode, status, priority, spec file name).
> Facts below were read from code, the existing QA kit (`00-README.md`, `stories/*.md`, `web/e2e/**`, `job-autofill/**`) and the design docs. Anything not confirmed is marked **unverified**. Where a story needs code that lives on a branch other than `version2`, the branch is named and the status is **partial** until it merges.

## 0. How to read this document

### 0.1 Rules every story obeys (non-negotiable, from `CLAUDE.md`)
- **E1:** the consultant submits. Kiwiply never submits, never auto-submits, never ticks attestation boxes. No story drives a submit button through the extension; where a submit happens it is the test acting *as the consultant*, on a **local fixture page**, and the story says so.
- **Never a live job site.** No automated story opens linkedin.com, greenhouse.io or any other real ATS. Real pages are reached only in the **manual** stories (3.11), by a person, never recorded by Playwright.
- **No sensitive PII in test data.** Names are invented, e-mails on `example.com` / `example.test`, no SSN, bank, tax id, passport, DOB or phone numbers anywhere; the PII-guard stories type an SSN-shaped string only to prove it is refused and nothing is stored.
- **O4:** personal and enterprise accounts are separate worlds; the same e-mail may hold both; nothing crosses. **O5/O6:** an assigned marketer sees their assigned consultants; an unassigned consultant is a generic **404**. Permission denials are **404, never 403** (the only 403-style answer is `CONSENT_REQUIRED`).
- **Capture real DOM before writing selectors** (ATS pages). Fixture pages for the extension stories are captured by a person first (3.1) and committed; no story guesses ATS markup.

### 0.2 ID scheme
`E2E-<AREA>-<NN>`. Areas: `ONB` (enterprise onboarding and setup), `STF` (staff onboarding, login, roles), `CON` (consultant profile, resume, applying with the extension), `MKT` (assign consultants to a marketer, manage resumes, applications, status), `XC` (cross-cutting). Numbers are never reused. Each story has a **covers** field naming the existing `ADM-/MKT-/CON-/PLT-/APP-` story (or `X<phase>.<n>` build story) it absorbs, so the recorded-story suite and this journey suite are mapped both ways.

### 0.4 Automation status vocabulary
- **runnable today**: every page, API and seed the story needs is on `version2`; the spec can be written and run now.
- **partial**: part of the path is built (or built on a named branch not yet on `version2`); the spec can be written with `test.fixme`/`test.skip` guards on the missing steps, and the story says which.
- **blocked**: cannot run end to end here, with the reason (not built, needs an external service, needs a fixture that does not exist yet, destructive to the shared seed).

## 10. Mapping to the recorded-story suite

The `*.story.ts` suite stays the per-page walkthrough with video; these journeys are the cross-page, cross-persona proofs and the P0 smoke. A story ID named in a **covers** field is not duplicated: the journey may call the same helpers (`_mkt.ts` `captureJob`, `_helpers.ts` `bff`, `stubJobSite`) and should import them rather than copy them.
