# ADR-024 — One org-owned Job Opportunity, adopted from a public posting layer; separate relationship records per stage

- **Status:** Proposed (2026-10-13) — awaiting owner review. No code or schema was changed.
- **Debate topic:** consultant Job Discovery / Job Matches / Assigned Opportunities over one Job (user brief 2026-10-13). Evidence: `D/50-job-architecture-assessment.md`.
- **Related:** ADR-001 (shared schema, `org_id`), ADR-008 (org_assignment), ADR-009 (resume ownership), ADR-010 (marketer prepares, consultant submits), ADR-011 (client data minimisation), ADR-012/021 (licenses, enforcement order).
- **Reversibility:** each decision is additive (nullable columns/new tables); D-1 and D-3 are the only ones that shape later work, and both can be revisited before Phase 2.

## Context
Two job worlds exist and are unlinked: org-owned `client_requirement` (backs every marketer page) and the global public `job_posting` (consumer product only). The enterprise job has no provenance, dedupe, lifecycle-by-source or visibility, no connector writes it, and no consultant surface exists. The pipeline stages (match, assignment, approval, submission, application) are disjoint tables without foreign keys between them, and several verified correctness gaps exist (assessment §3 F1–F15).

## Options evaluated

| Criterion | **A** One global canonical `Job`, org relationships reference it (user's proposal, taken literally) | **B** Public/source postings + org-owned opportunities linked by identity | **C (recommended)** = B with the org-owned `client_requirement` as the single in-tenant canonical job, adoption by copy-on-adopt, occurrence table for provenance |
|---|---|---|---|
| Correctness | One row shared by all tenants: org-edited rate/notes/status must live elsewhere; private client requirements cannot be global | Correct, two layers | Correct, two layers, clear ownership |
| Tenant isolation | **Breaks** five verified invariants (assessment §4): `org_id NOT NULL`, composite FKs, repo contract, `TalentSchemaIT`, no-`@Filter` | Holds | Holds; only public fields cross, by copy |
| Reuse of existing code | Rewrite all 12 `mkt/*` services and 46 repositories | Reuse everything built | Reuse everything built |
| Query performance | Global table needs per-org overlay joins on every discovery query | Org-local search; public search separate | Org-local search (SQL), public layer already FULLTEXT |
| Dedupe | Global dedupe is natural | Per-layer dedupe | Public layer dedupe exists (`dedup_key`); per-org soft dedupe + occurrence unique key |
| Workflow flexibility | Org status/notes need a per-org overlay anyway (= option B in disguise) | High | High |
| Migration | Backfill + FK rewrite of every table | Additive | Additive |
| Maintenance | Highest (global lifecycle + per-org overlay) | Medium | Medium–low |

**Rejected:** A, because it solves a problem (cross-tenant dedupe) the enterprise flows do not have, at the cost of the platform's core isolation rule. **Chosen: C.**

## Decisions
- **D-1 Canonical identity inside a tenant.** `client_requirement` (with `requirement_skill`, `mkt_job_meta`) is **the** Job Opportunity of an organization. All three consultant views read it. No second job table inside the enterprise domain.
- **D-2 Source vs identity.** Add `org_job_source_occurrence(org_id, requirement_id, stream_id?, source_label, external_id, url, apply_url, first_seen_at, last_seen_at, status ACTIVE|MISSING|EXPIRED, payload_hash)` unique `(org_id, stream_id, external_id)`. A job listed on several sources = one `client_requirement`, many occurrences. `client_requirement` gains `first_seen_at`, `last_seen_at`, `closing_date`, `closed_reason`. Closing from the source never deletes: occurrences go `MISSING` → job `CLOSED` only when **all** occurrences are gone for N days (setting).
- **D-3 Public pool = existing global `job_posting`; org adopts.** `job_posting` stays global, public fields only. An org "adopts" a posting (marketer or an auto-rule on a stream) by creating a `client_requirement` that **copies** the public fields and stores `posting_id` (nullable, no FK across the global/tenant boundary by design, documented). Source updates flow to the adopted job field-by-field only where the org has not overridden the field (`field_overrides` JSON). Copy-on-adopt makes org jobs immune to the posting's 7-day deletion and cannot leak tenant data back to the global table.
- **D-4 Dedupe.** Never "same title + same company ⇒ same job". Three layers: (1) **hard** — unique `(org_id, stream_id, external_id)` on occurrences; (2) **candidate** — `dedup_key` (normalised client\|title\|location) on `client_requirement`, same key within an org raises a *merge suggestion* (UI + `mkt_job_alert`), never an automatic merge; (3) **manual** merge by a marketer with `requirements.manage`, preserving all occurrences and relationship rows (re-pointed in one transaction, audited). Different client or different end-client = never a candidate.
- **D-5 Org-private vs public.** Org-private jobs (client requirements, manual entry, client portal) are `client_requirement` rows with `source=MANUAL|CLIENT_PORTAL|IMPORT`; public jobs enter only through D-3. There is **no `visibility` column on `client_requirement`** and no NULL-org rows. Anything shown to a consultant is the org-scoped row; client contact, internal owner, bill rate and marketer notes are never in a consultant DTO unless the org setting `consultants.see_rate` allows the rate.
- **D-6 Match = `requirement_match` (ConsultantJobMatch), persisted + recomputable.** Keep the unique `(org, requirement, consultant)`. Add `components` (JSON: skills, experience, location, availability, work-authorization fit), `missing_skills`, `algorithm_version`, `resume_id/resume_version_used`, `calculated_at`, `stale_at`, `hard_eligible` (boolean) + `ineligible_reasons`. **Hard constraints** (work-authorization, availability window, closed job, licensed-feature absent) set `hard_eligible=false` and exclude the row from ranking views; **soft** preferences only change score. One `JobMatchScorer` (extracted from the three current copies) is the only writer of `score`. Hybrid refresh: persisted rows, marked `stale_at` by events (job updated, resume/profile version changed, availability changed), recomputed in a per-org scheduled job through `TenantScoped` and on demand for a single pair.
- **D-7 Assignment = `requirement_match.status=ASSIGNED` + `mkt_opportunity` (ConsultantJobAssignment).** One `OpportunityAssignmentService` replaces the three assign paths. Add to `mkt_opportunity`: `state` (lifecycle in doc 52), `viewed_at`, `decline_reason`, `info_request`, `marketer_note`, `consultant_note`, `priority`, `due_at`, `assigned_by_member_id`, `version` (`@Version`). A job may be assigned to many consultants; one consultant+job pair has exactly one row (already unique). **Reassignment of a consultant's marketer** is preserved by a new `marketer_assignment_event` history (open decision Q-2: adopt `org_assignment` per ADR-008 instead).
- **D-8 Saved jobs.** New `org_saved_job(org_id, consultant_id, requirement_id, saved_at, note)` unique `(org, consultant, requirement)`; consultant-OWN only; separate from `requirement_match`. (The personal product's "SAVED" application row is not reused: different owner and lifecycle.)
- **D-9 Separate events, linked rows.** Concepts stay in separate tables, linked by explicit ids: `requirement_match.id` → `mkt_opportunity.match_id` (exists) → `mkt_submission.opportunity_id` (new) → `talent_application.submission_id` (new, nullable) → `talent_interview.application_id` (exists) → `talent_placement.application_id` (new). No single "status" field spans stages. Status history = the existing `*_event` tables plus a read-only union view for timelines (`TimelineFeed`, already in `packages/ui`).
- **D-10 Submissions are records; the consultant authorizes.** `mkt_submission` (ClientSubmission) keeps `approval_state`; the transition AWAITING_APPROVAL → APPROVED/REJECTED may be performed **only** by the consultant (`submissions.authorize`, OWN) through a `con` endpoint, or by an org admin with `submissions.authorize_override` (audited, HIGH). Approval is bound to `(resume_id, resume_version)`; an edit that bumps the version moves un-submitted approvals to `AWAITING_APPROVAL` (`RESUME_CHANGED` event); **revocation** moves un-submitted records to `REVOKED` and leaves SUBMITTED/CLIENT_REVIEW+ records untouched but flagged `authorization_revoked_at` (they happened; the audit trail keeps them; the marketer is told to withdraw externally). A live-submission unique key `(org, consultant, requirement)` closes F2.
- **D-11 Applications.** `talent_application` stays the org-side JobApplication (+ events = ApplicationStatusHistory). Three entry paths create it idempotently on `(org, requirement, consultant)`: consultant direct ("I applied"), marketer-assisted (consultant submits after authorizing), client submission recorded. A second path finds the existing row and appends an event. Linking to the consultant's personal `application` row (if any) is optional (`personal_application_id`, no FK; open decision Q-3).
- **D-12 Concurrency/idempotency.** `@Version` on `requirement_match`, `mkt_opportunity`, `mkt_submission`, `talent_application`; DB unique keys are the source of truth and `DataIntegrityViolationException` is translated to the same 409 as the pre-check (shared `ConflictTranslator`); `Idempotency-Key` required on assign/submit/authorize POSTs (24 h `IdempotencyService`). Two marketers assigning the same pair → second returns the existing row (200, `alreadyAssigned=true`), never 500, never two rows.
- **D-13 Role namespaces.** Marketer = `mkt` (done). Consultant = **`con`**: `/api/orgs/{orgId}/con/...`, `service/ent/con/`, `web/rest/ent/con/`, tables `con_*` for consultant-only state, BFF `app/api/orgs/[orgId]/con/**` (replaces `me-workspace` in the consultant handoff). Shared role-neutral logic lives in `service/ent/jobs/` (`JobQueryService`, `JobMatchScorer`, `OpportunityAssignmentService`, `SubmissionAuthorizationService`) and is called by `mkt` and `con` facades with their own scope objects (`MktScope`, new `ConScope`). Each role's facade owns its DTOs (a consultant DTO never contains marketer notes of other consultants, other consultants' scores, client contacts).
- **D-14 Entitlements.** Rule-based discovery, assigned opportunities, manual matching and application tracking are the **free core** (D/21:76, D/37:31). AI-scored matching (`ai.job_matching`) and tailored-resume features are licensed overlays. Because `AuthzStep` 6–8 and 10–11 have no implementers today, **no AI-scored UI ships until `EntitlementCheckStep` + `@RequiresFeature` exist** (Phase 6 dependency X5.6); the consultant pages meanwhile show rule scores labelled "Rule-ranked". UI hiding is presentation only; the API check is mandatory.
- **D-15 Frontend.** One `JobDetailsView` (role-neutral folder `web/src/components/ent/jobs/`), rendered in a right-side `SideSheet` (overlay, 520 px) on ≥1024 px and as a dedicated route/screen (`/w/consultant/jobs/[id]`, back action) below 1024 px (mobile + tablet, per the user's brief; `useNarrow` today breaks at 767 px and must gain a `useCompact` 1023 px variant). Sections are selected by a `context` prop (`discovery | match | assignment | submission`) and by the server's per-context DTO, not by hiding fields client-side.

## Consequences
- **Positive:** reuses every existing table and page; tenant isolation unchanged; connectors (Phase 16) have a defined landing place; the pipeline gets real foreign keys and consultant authorization (closes F1–F8).
- **Negative:** two layers (public posting, org job) need an adoption flow and an override model; backfill of `external_id/first_seen_at` for existing seeded rows is synthetic; `con` is another API namespace to cover in `OrgIsolationIT`.
- **Risks:** adopted copies diverge from the public posting (mitigated by `field_overrides`); merge of duplicate jobs touches many tables (mitigated: one transaction, audited, reversible within 24 h via event log); scorer extraction changes numbers on existing pages (mitigated: behind `algorithm_version` and a golden test of the three current formulas).
- **Rollback:** every schema change is additive and guarded by flags `flag.enterprise.marketing` (live) and a new sub-flag `flag.enterprise.consultant_jobs` (consultant pages) — turning the flag off hides `con` routes; nothing destructive.

## Open decisions for the owner (safe default in brackets)
- Q-1 Consultant API namespace `con` vs `me` [`con`, to mirror `mkt`].
- Q-2 Marketer reassignment history: new event table vs finally implementing `org_assignment` (ADR-008) [event table now, migrate later].
- Q-3 Link to the consultant's *personal* `application` row [no link in v1].
- Q-4 May a consultant see the client bill/pay rate? [setting, default hidden; show the "pay/rate" range only when the marketer marks it visible].
- Q-5 Should adopting from the public pool be automatic for a stream (auto-adopt rules) or always manual [manual in v1, auto-adopt in Phase 16].
- Q-6 Who may override a consultant's authorization (org admin) [yes, HIGH-risk audited action, off by default].
