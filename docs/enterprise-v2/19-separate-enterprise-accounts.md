# 19 - Separate enterprise accounts (decision O4): data model, impact inventory, security, migration, phased plan

> Status: design, 2026-10-14 (analysis only, no code changed). Decision: **O4** in `08-decisions-for-user.md`.
> Audience: a Sonnet implementation agent. Every path below is relative to the repo root; `api/` = `api/src/main/java/com/dossier/api/`.
> Read order: section 0 (rules), 1 (data model), 2 (inventory), then the phase you are building (section 7).

## 0. The decision, as rules (these are the acceptance criteria for every phase)

User decision 2026-10-14 (final): enterprise accounts and personal Kiwiply accounts are **separate and not connected**.

| # | Rule |
|---|---|
| R1 | The same email may exist once as a personal account and once **per organization** as an enterprise account. Separate rows, separate passwords, separate data. |
| R2 | Creating an enterprise account (owner via app-admin Create organization, employee via Org Admin "Create account now", or accepting an invitation) **never** reads, attaches, links, changes or reveals a personal account. |
| R3 | Resumes, Gmail inbox connection, settings, notifications, AI usage, billing and subscriptions made in an enterprise account live only there, and never show on kiwiply.com (and vice versa). |
| R4 | The host decides the world: a **tenant host** authenticates **enterprise accounts of that org only**; a **platform host** (kiwiply.com, www, app, api) authenticates **personal accounts only** (plus the extension exception in R6). |
| R5 | One person in two organizations holds two enterprise accounts (one per org). Sarah's Administration + Marketing are two **roles** (`org_member_role`) on **one** enterprise account and stay as they are. |
| R6 | The browser extension connects with **one account at a time** (personal OR enterprise); the person switches by connecting the other. Nothing is shared between the two. |
| R7 | Nothing may tell a caller whether an email has a personal account (or an enterprise account elsewhere). |

## 1. Data model: options, recommendation, mechanics

### 1.1 Facts in the code that drive the choice

* `jhi_user` (`api/domain/User.java`, `00000000000000_initial_schema.xml`): `login` varchar(50) **globally unique** (`ux_user_login`), `email` varchar(191) **globally unique** (`ux_user_email`).
* The JWT subject is the **login**, and the user id travels as claim `uid`. Both are used as keys all over the system:
  * ~31 tables hold an FK to `jhi_user.id` (`user_id`): `resume`, `resume_doc`, `resume_doc_version`, `resume_access`, `resume_match`, `resume_tailor`, `resume_view_event`, `resume_ai_proposal`, `bio`, `profile_item`, `profile_suggestion`, `application`, `application_event`, `application_note`, `interview`, `job_fit`, `job_match`, `job_match_setting`, `job_feedback`, `field_cache`, `ai_answer`, `inbox_connection` (PK = user id), `inbox_message`, `inbox_folder_state`, `notification`, `notification_preference`, `onboarding_draft`, `subscription`, `refresh_token`, `org_member`, `org_group`, `org_domain`, `org_join_code`, `org_invite_batch`, `organization.created_by_user_id`, `customer_note`, `jhi_user_authority`.
  * Tables keyed by the **login string**: `ai_usage` (`ux_ai_usage_login_period`), `org_audit_event.actor_login`, `created_by_login` (resume doc), `user_login` columns, `AbstractAuditingEntity.created_by`.
* `SecurityUtils.getCurrentUserLogin()` then `userRepository.findOneByLogin(...)` is the idiom in ~93 files (services and tests). `findOneByEmailIgnoreCase` (returns `Optional`, so **two rows with one email throw `IncorrectResultSizeDataAccessException`**) is called from 11 production files (see 2.1).
* Existing precedent for a scoped uniqueness key: `org_member.active_user_key` is a MySQL `GENERATED ALWAYS ... STORED` column with a unique index (`20261013010000_org_core.xml` line ~140). The same technique works here.

### 1.2 Options

| | (A) Keep `jhi_user`, add nullable `org_id` | (B) New `org_account` identity table referenced by `org_member` |
|---|---|---|
| Idea | Enterprise account = a `jhi_user` row with `org_id = <org>`; personal = `org_id IS NULL`. Uniqueness becomes `(scope, email)`. | Enterprise identity lives in its own table with its own password, tokens and ids. `jhi_user` stays personal-only. |
| Existing FK users (the ~31 tables) | **Unchanged**: every table already points at `jhi_user.id`; an enterprise account is just another id. Resumes, inbox, notifications, AI, refresh tokens, audit all work with zero schema change. | Every feature that today stores `user_id` for a consultant (resumes, builder, job matches, applications, inbox, notifications, onboarding, AI) would need a polymorphic owner (`owner_kind` + `owner_id`) or a duplicate set of tables. 30+ tables and their services, tests and the resume builder. |
| JWT / security | Unchanged shape: `sub` login, `uid` id, `tid` for enterprise. | New principal type through Spring Security, `SecurityUtils`, `@PreAuthorize`, audit, caches, every `findOneByLogin`. |
| Separation guarantee | By data (different rows) + a **world check** in the auth layer. Needs discipline: a personal-only query must exclude `org_id IS NOT NULL` where it lists users. | Structural: a personal lookup cannot even see an enterprise row. |
| Risk | Medium: ambiguity bugs (`findOneByEmailIgnoreCase`), admin/analytics lists that must exclude enterprise rows. Both are mechanical and testable. | High and wide: the largest rewrite in the product for the same user-visible result. |
| Size | L (about 10 stories) | XL (about 25 stories), touches the shipped resume builder |

**Recommendation: (A).** Same behaviour for the user, a fraction of the blast radius, and every shipped feature keeps working unchanged. The separation requirement is satisfied because an enterprise account is a **different `jhi_user.id`** with its own password hash, tokens, resumes, inbox row, notifications and AI counters. Option (B) is only worth it if a later requirement says enterprise identities must live in another database; nothing today says so.

### 1.3 Schema (all additive Liquibase, file `2026111x_separate_enterprise_accounts.xml`)

```
jhi_user
  + org_id               BIGINT NULL            -- NULL = personal account; non-NULL = enterprise account of that organization
  + account_scope_key    BIGINT GENERATED ALWAYS AS (IFNULL(org_id, 0)) STORED
  FK  fk_user_org  org_id -> organization(id)   ON DELETE RESTRICT  (an org with accounts cannot be hard-deleted; deletion goes through the erase flow, 3.8)
  IDX ix_user_org (org_id)
  UNIQUE ux_user_scope_email (account_scope_key, email)      -- new
  DROP   ux_user_email                                        -- replaced by the line above (see note)
  KEEP   ux_user_login                                        -- login stays globally unique (it is the JWT subject and the key of ai_usage / audit)
organization
  + account_mode         VARCHAR(10) NOT NULL DEFAULT 'SHARED'    -- SHARED (legacy: members are personal accounts) | SEPARATE (members are enterprise accounts)
```
* **Dropping `ux_user_email` is the one non-additive step.** It only *relaxes* a constraint, and the replacement is created in the same changeset first (create `ux_user_scope_email`, then drop). Include a Liquibase `rollback` that recreates `ux_user_email` (fails safely if duplicates exist, which is the right signal). Call this out in the PR description (CLAUDE.md says additive migrations).
* Existing rows get `org_id = NULL`, so scope 0 and the new unique index is satisfied by every existing row: the migration is behaviour-neutral until an enterprise account is created.
* `email` stays nullable (MySQL treats NULLs as distinct in the unique index, as today).
* **Login for enterprise accounts** (`login` is globally unique, max 50, and is the JWT `sub` and `ai_usage` key): `ent#<orgId>#<email>` when it fits in 50 chars, otherwise `ent#<orgId>#<first 16 hex of sha-256(email)>`. The `#` character is **rejected by the personal registration regex** (`Constants.LOGIN_REGEX`), so a personal sign-up can never collide with, squat or impersonate an enterprise login. Add a guard in `UserService.registerUser` / `findOrCreateGoogleUser` that rejects any login starting with `ent#`. The enterprise login is never typed by a human: people sign in with their **email** on their tenant host.
* **Invariant (tested + a nightly check query):** for every `org_member` row of an organization with `account_mode = 'SEPARATE'`, `jhi_user(org_member.user_id).org_id = org_member.org_id`. An enterprise account has exactly one organization for life. A composite FK cannot express it because legacy `SHARED` orgs use personal accounts; enforce in `OrgMemberWriter`/the services plus `EnterpriseAccountInvariantIT` plus an admin health query.
* `account_mode` rule: `AdminOrgService.create` sets `SEPARATE` for every new org; the enterprise switch (`flag.enterprise` allow-list) refuses an org that is still `SHARED` (it must be migrated, section 5). Test fixtures keep creating `SHARED` orgs (the column default) so the current ITs are untouched.

### 1.4 How each identity concern works

| Concern | Rule (recommended) |
|---|---|
| **Login resolves the account from the HOST** | `TenantContextHolder.current()` is already set by `TenantResolverFilter` from `X-Kiwiply-Host` before `AuthenticateController.authorize` runs (it is what `TenantSessionService.bindingForLogin` reads today). `DomainUserDetailsService.loadUserByUsername` reads it: **tenant** -> `findEnterpriseByEmail(orgId, email)` (or by login only if `user.org_id == orgId`); **platform** -> `findPersonalByEmail(email)` / `findPersonalByLogin(login)` (`org_id IS NULL`). Unknown host -> the existing generic refusal. A credential for the other world is **indistinguishable from an unknown user** (same `BadCredentialsException`, same timing: `DaoAuthenticationProvider` already hashes against a dummy for unknown users). |
| **Repository API** | Delete `findOneByEmailIgnoreCase`, `findOneWithAuthoritiesByEmailIgnoreCase`, `USERS_BY_EMAIL_CACHE` keyed by email alone. Add `findOneByOrgIdIsNullAndEmailIgnoreCase`, `findOneByOrgIdAndEmailIgnoreCase(Long orgId, String email)` and `...WithAuthorities...` variants. Cache key = `scopeKey + ':' + email`. An ArchUnit rule (`TechnicalStructureTest`) forbids reintroducing an email lookup without a scope. Removing the old method makes the compiler list all 11 call sites. |
| **JWT claims** | `tid` is present **if and only if** `user.org_id != null`, and then `tid == user.org_id` (set at issue time from the user row, not from the host; the host is then checked against it by the existing `TenantTokenBinding` decoder rule). `hid` as today for tenant sign-ins. `pcr` unchanged and now only ever true for enterprise accounts (temp passwords exist only there). New claim `ext=1` on extension tokens (6.3). A personal token never has `tid`. |
| **Token world check (cross-world confusion)** | Platform host: a token with `tid` is refused (`401 TOKEN_WRONG_WORLD`) on every route except the extension routes when `ext=1`. Tenant host: a token **without** `tid` is refused (`401 TOKEN_WRONG_WORLD`) on every route (this removes today's "no tid on a tenant host may call user-scoped `/api/account`" hand-off and the tid-less invite token, see 2.3). Implemented in `TenantTokenBinding`/`TenantTokenBindingFilter`, which already hold the tid-vs-host logic. |
| **Refresh tokens** | `refresh_token` rows are per `user_id`, so per account already. `AuthenticateController.refresh` additionally loads the user and rejects the refresh when `user.org_id != tid` (defence against a row edited by hand). `revokeAllForUser` revokes one account only; changing the password of the personal account does not log out the enterprise account and vice versa. |
| **Password reset** | `UserService.requestPasswordReset(mail)` becomes `requestPasswordReset(scope, mail)`; `AccountResource.requestPasswordReset` reads the scope from the host. The reset key lives on the account row, so a reset email can only ever reset the account of the world that asked. On a tenant host the link is built with `TenantUrls.base(org)` (already specified) and the mail uses the Enterprise theme. Always answer 200 with the same body (R7). |
| **Email verification** | Personal: unchanged (`/api/register`, `activation_key`). Tenant hosts: **`/api/register` is refused** (404 on a tenant host; accounts come only from admin creation or invitation). Admin-created accounts stay activated without verification (O1/O2 unchanged); an invitation proves the address by token possession; changing the email later re-verifies per account. |
| **Self-service email change** | `AccountResource.saveAccount` uniqueness check becomes scope-aware (`EmailAlreadyUsedException` only inside the same scope). |
| **`jhi_user_authority`** | Per account row. Enterprise accounts get `ROLE_USER` only. They must **never** receive `ROLE_ADMIN`/platform authorities (guard in `UserService.createEnterpriseAccount` + test). Org roles stay in `org_member_role`. |
| **"User-scoped routes" when two accounts share an email** | Every user-scoped route (`/api/account`, `/api/profile/**`, `/api/resumes/**`, `/api/notifications`, `/api/inbox/**`, `/api/billing/**`, `/api/ai/**`) resolves the user from the token's `sub`/`uid`, never from the email, so the two accounts never meet. Rules: the route family `/api/orgs/{orgId}/**`, `/api/me/tenant`, `/api/ent/**` need an enterprise token of that org; the family `/api/billing/**` (personal Stripe), `/api/account/delete`, `/api/inbox/**` (the personal-plan inbox routes) need a personal token, and an enterprise token gets `404`. Enterprise accounts use `/api/orgs/{orgId}/me-workspace/**` for inbox and resumes. |
| **Admin side** | Platform admin user/customer lists, analytics and counts (`CustomerAdminService`, `AdminAiQuotaService`, `AdminUserActionService`, `UserRepository.countByActivatedIsTrue`, `countByCreatedDateAfter`, `findAllByIdNotNullAndActivatedIsTrue`) must filter `org_id IS NULL`. Enterprise accounts appear only under their organization (`/admin/organizations/[id]`). |

## 4. Security review

| Threat | Control |
|---|---|
| **Account enumeration** (does this email have a personal account?) | (1) tenant login for a credential that only exists in the other world returns the same 401 body and similar timing as an unknown user; (2) forgot-password always 200 with a fixed body and sends mail only if the in-scope account exists; (3) invitation and "Create account now" never branch on personal rows (today `OrgAccountService.create` returns `INVITED` for a known address, which **is** a leak and is removed); (4) sign-up on kiwiply.com is unchanged (a personal duplicate still says "email already used", as today); (5) registration on a tenant host is 404; (6) platform admin Create organization stops returning `EXISTING`; (7) error codes `NOT_A_MEMBER`/`TEMP_PASSWORD_EXPIRED` are only reachable after a correct in-scope password. |
| **Login rate limits per account** | `RateLimitFilter`/`FixedWindowRateLimiter`/`TenantRateLimiter` exist. Add a failed-login counter keyed by `(scope, normalized email)` plus the IP bucket already there, so hammering `acme.kiwiply.com` for `a@x.com` cannot lock the personal `a@x.com`, and the other way round (no cross-world denial of service). Counters live per host world: key prefix `P:` or `E<orgId>:`. |
| **Credential stuffing across the two worlds** | A stolen personal password does nothing on a tenant host (not looked up there) and vice versa. People who reuse a password across both are not protected by us; mitigation: an enterprise temp password is random, `pcr` forces a change, and the set-password page uses the same password rules. Admin MFA (`AdminMfaService`) applies to personal admin accounts only. |
| **Cross-world token confusion** | `tid` iff enterprise (1.4). Platform host rejects a `tid` token except `ext=1` extension routes; tenant host rejects a token without `tid`, and a `tid` of another org (`TOKEN_TENANT_MISMATCH`, existing). The refresh path re-checks `user.org_id == tid`. New test class `WorldBindingIT` covers all 2x2 cells (personal/enterprise token x platform/tenant host x user-scoped/org-scoped/extension route). |
| **Extension token blast radius** | `ext=1` enterprise tokens are accepted only on an allow-listed set of routes (6.3) of their own org; they cannot reach `/api/orgs/{tid}/members`, admin, billing or console routes. Personal extension tokens are unchanged. |
| **Temp-password flow** | Unchanged and enterprise-only: `password_change_required`, `password_temp_expires_at`, `pcr` claim, `PasswordChangeRequiredFilter`, `InviteNeverSetsTempPasswordIT`. A personal account can never carry the flag (guard in `UserService`; `PersonalNeverHasTempPasswordTest`). |
| **Invite takeover** | The public accept endpoint uses the invite token as the only credential: token entropy and hashing already exist (`InviteTokens`); keep one-time use, expiry, `JoinRateLimiter`, and show the invited email read-only. A forwarded invite lets the forwardee create the account: same as today's trust model; the Org Admin can revoke. |
| **Login squatting** | The `ent#` prefix is rejected by personal registration and Google creation. |
| **Admin tools** | All admin lists exclude enterprise rows by default; "impersonate/view as" does not exist, keep it that way. |
| **Audit** | `org_audit_event.actor_login` now shows `ent#<org>#...`; the audit UI must display the person's name/email from the user row, never the login. |

## 6. Extension design (one account at a time)

### 6.1 Storage and display
* Keep the single `trackingAuth` session. Add to it `{kind: "PERSONAL"|"ENTERPRISE", orgId, orgName, email, userId}` (written at connect, from the handoff message). Account-bound caches (`ACCOUNT_KEYS`, `ws:*`) are cleared whenever `userId` changes; compare **user ids**, not emails or usernames (two accounts, one email).
* Panel header shows an **account chip**: `Personal` or `Acme · Enterprise`, with the email underneath and a "Switch account" action. The Personal/Org `<select>` is removed. Options page "Account status" shows email + kind + org.
* Switching = connect the other account: the web side opens `kiwiply.com/connect` (personal) or the tenant host's "Connect extension" (enterprise), the extension replaces the session and clears the previous account's caches. No second session is stored (decision R6; storing both was rejected: it would keep an enterprise token alive on a personal device state and adds a path for data to cross).

### 6.2 Server contract
* `GET /api/profile/version` returns `account: {kind, orgId, name, consultant, marketer}` plus the existing `version`/`plan`. Personal -> `workspaces: []`. Enterprise -> `workspaces: [one]` for one release (old extension builds keep working), then removed. `X-Kiwiply-Workspace` / `WorkspaceHeaderFilter` (backlog X9.9) are **not built**: the token already identifies the account and the org (`tid`), so the header is unnecessary. Mark X9.9's header part superseded.
* The extension keeps calling `api.kiwiply.com` (a platform host). Its enterprise token carries `tid` and `ext=1`, and the world check (`TenantTokenBindingFilter`) accepts it on the platform host; `AccountKindRouteFilter` then holds it to `ExtensionRoutes`, the list of the endpoints the extension REALLY calls (corrected from the first draft of this section, which named `/api/resumes/**`, `/api/application*`, `/api/field-cache*`, `/api/fill-telemetry` and `/api/bug-report`; the client report `docs/HANDOFF-ENT-ACCOUNTS-TRACK-B-REPORT.md` question 3 was right): `GET|PUT /api/profile`, `GET /api/profile/version`, `/api/profile/resumes[/{id}]`, `POST /api/resumes/{id}/file`, `/api/profile/applications[/{id}[/attachment]]`, `POST /api/profile/field-caches/sync`, `POST /api/profile/suggestions`, `GET /api/ai/usage`, `POST /api/ai/{draft,job-fit,parse-resume,resume-match}`, `POST /api/telemetry/fills[/{id}/correction]`, `POST /api/bug-reports`, `POST /api/refresh`, `POST /api/logout`, and for its OWN organization only (`tid`): `/api/orgs/{tid}/me-workspace/**`, `GET /api/orgs/{tid}/con/opportunities[/{id}]`, `POST /api/orgs/{tid}/con/opportunities/{id}/{viewed,interest,decline,request-info,applied,link,unlink}`, `GET /api/orgs/{tid}/mkt/opportunities/options`, `POST /api/orgs/{tid}/mkt/opportunities/from-extension`. Every other route, method or organization is the generic 404 (`ExtensionRoutesTest` pins both directions). A personal extension token has no `ext` claim and keeps its current route set. `ext=1` enterprise tokens refresh through `POST /api/refresh` on the platform host and keep `ext` and `tid` (the refresh token must belong to an account whose `org_id` is its `tid`, on an active seat).
* `account` (as built, S6): `{kind: "PERSONAL"|"ENTERPRISE", orgId, name, consultant, marketer}`. Personal: `{kind: "PERSONAL", orgId: null, name: null, consultant: false, marketer: false}` and `workspaces: []` (a personal account holds no seat in a SEPARATE organization; one in a legacy SHARED organization keeps the old list). Enterprise: `name` = the organization's display name, the two flags from the seat's roles (false when roles are not read from data or the marketing module is off), `workspaces` = that one organization for one release. The route stays reachable for marketer-only accounts.
* **`X-Kiwiply-Workspace` / `WorkspaceHeaderFilter` (backlog X9.9, header part) are SUPERSEDED and not built**: the token identifies the account and its organization.

### 6.3 Connect handoff for an enterprise account
`externally_connectable` only lists kiwiply.com origins, and custom tenant domains cannot be listed. So:
1. On the tenant host, "Connect extension" calls `POST /api/extension/connect-code` (enterprise session) -> one-time code, 60 s, stored hashed, bound to `user_id`, `tid`, no other data.
2. The browser opens `https://kiwiply.com/connect?code=...` (the API builds the link: `TenantUrls.base(null)`); the `/connect` page takes the code out of the address bar and the platform BFF exchanges it (`POST /api/extension/token` with `{code}` -> `POST /api/extension/connect-code/exchange`, public, single use, rate-limited) for an `ext=1`, `tid` pair and hands it to the extension through the existing `externally_connectable` message (or the Firefox relay).
3. `/api/extension/session` (personal, from the personal cookie) is unchanged apart from carrying the account (below); an enterprise token gets the generic 404 there.
4. **The handoff message** (answers question 1 and 2 of the client report): the new fields live INSIDE the existing `tokens` object, next to `access` and `refresh`: `{type: "KIWIPLY_CONNECT", tokens: {access, refresh, kind, userId, email, orgId, orgName, username}}`. Personal: `kind: "PERSONAL"`, `userId`, `email`, `username` (the login, as before), no `orgId`. Enterprise: `kind: "ENTERPRISE"` with a positive integer `orgId` and `userId` (the BFF refuses to hand over anything else), `orgName` = the organization display name, `email`, and never a `username` (the synthetic `ent#` login is never sent). The API returns the same fields beside `accessToken`/`refreshToken` from `POST /api/extension/session` and the exchange; the web BFF `web/src/app/api/extension/token` maps them (`web/src/lib/extension-handoff.ts`).
5. **Connect code**: 256 random bits (base64url, 43 characters), 60 seconds, stored as SHA-256 only in `ext_connect_code` (`user_id`, `org_id`, `expires_at`, `used_at`), spent by one atomic conditional update, minting limited to 10 per account per 5 minutes, exchange to 60 per client address per 5 minutes (`dossier.connect-code.*`). Every failure of the exchange is the same empty 401; minting is the generic 404 for anything but an enterprise session of an active seat. The exchange also refuses an account that must still change a temporary password.
The Firefox `connect-relay` content script keeps working (same page).

### 6.4 Engine
`JAF.workspace.modeOf(workspaces, setting)` is replaced by `modeOf(account)` (pure function, unit tests in `job-autofill/test`): personal -> today's drawer; enterprise with `marketer && !consultant` -> marketer facade; `consultant` -> fill + Jobs tab. Everything else in `workspace.js` (trim capture, URL keys, matching) is unchanged. No new engine dependency. The fill engine reads bio/resumes from the connected account's mirror, so an enterprise consultant autofills with the enterprise account's profile and resumes.
